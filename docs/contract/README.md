# QuestionPackage v1

The interchange format a question is authored in, imported from and validated
against. **The importer does not exist.** Nothing in the application reads any of
this. It is here to be argued with before a user interface is built on top of it.

The goal it serves, stated once so every decision below can be checked against
it: *a complete question can be authored as JSON outside Marginal, validated,
reviewed as a coherent authored set, and imported, without anyone editing
`essay-content.js` or reading the application's source.*

## What is here

| file | what it is |
| --- | --- |
| `authoring-guide.md` | **generated.** Every field, what it is for, what omitting it costs, a good example and a bad one |
| `question-package.schema.json` | **generated.** JSON Schema, for an author's own tooling |
| `template-causal.json`, `template-judgement.json`, `template-write-only.json` | **generated.** The three shapes a question is authored into |
| `example-*.json` | **generated.** All nineteen questions in the bank, converted from source |
| `shared-libraries.json` | **generated.** The libraries a package references: vocabulary, concepts, lessons, evidence, syllabus, resources, sentence shapes |
| `library-manifest.json` | **generated.** Ids and states, no bodies. What a validator checks a `requires` block against |
| `invalid-demo.json` | **authored to be wrong.** One fault of every kind |
| `decisions.md` | the decisions taken, and what each one rules out |
| `migration.md` | how the questions in source get out of source |

Generated means generated by `node build.js`, above the point where anything
reaches disk, and compared by `tests/t18.mjs`. Editing one of them by hand fails
a gate.

    node tools/contract/packagize.js               convert every question
    node tools/contract/packagize.js mkt-01        convert one
    node tools/contract/validate.js <package.json> validate one or many

## One field definition, four artefacts

`tools/contract/fields.js` is the contract. The JSON Schema, the authoring guide,
the three templates and the validator's enum and ref checks are all generated
from it or driven by it.

This is not tidiness. Four hand-maintained descriptions of one format drift, and
the drift is invisible until an external author follows the guide and the
validator rejects what they wrote. `tests/t18.mjs` regenerates all four and
compares, so drift fails a gate rather than a person.

Every field answers ten questions, because those are the ten an external author
has: whether it is required, what it means pedagogically, whether it belongs to
the question, a pathway or a shared library, its allowed values, which ids it may
reference, which student surface consumes it, whether omitting it invalidates the
package or reduces a capability, a good example, a bad example, and whether a
student reads the words.

## Capability, not a score

Six capabilities, reported independently.

| capability | what a student can be given |
| --- | --- |
| `importable` | the package parses, resolves and can be stored |
| `writing-ready` | the question can be given to a student to write against |
| `pathway-guided` | a student can choose between authored arguments and be guided through one |
| `learning-complete` | a student who does not know the content can be taught it here |
| `assessment-complete` | the student can see what the answer must accomplish and how it is marked |
| `evidence-complete` | every argument has evidence carrying a source |

A question climbs them independently, and one number would average away the row
that matters. What the nineteen currently report:

    mkt-01, fin-01, hr-01     Guided - missing learning-complete, evidence-complete
    the ten write-only        Writing ready - missing pathway-guided, learning-complete,
                                              assessment-complete, evidence-complete
    the six ancient history   Importable - a stem, its requirements and nothing else

Falling short of a capability is not an error and is never a silent downgrade.
The package keeps saying what it is; the report says what it reaches; publishing
at a lower capability is somebody's explicit action.

## Missing support is not a malformed package

A judgement question with no judgement sentence shapes is structurally valid. The
engine has six shapes and every one of them is causal, so `esShapeFor` matches
nothing and the shape panel is withheld while the student writes. That is correct
behaviour and a real gap, so the report names it:

    SUPPORT UNAVAILABLE - not a fault in the package
      sentence shapes: no shape is authored for the judgement family, so the
      shape panel is withheld while a student writes this question

`mkt-02` imports, and says that.

## The four severities

| severity | means | imports |
| --- | --- | --- |
| `error` | the package is wrong | no |
| `blocked` | the package is right and the library is not ready | no, and there is nothing in the package to fix |
| `shortfall` | well formed, and something it asks for cannot be given in full | yes, and it is recorded |
| `warning` | worth recording | yes |

**Nothing is written before the whole set has been read.** Parse, validate and
resolve every package in an import before any of them could publish. Every check
runs; none short-circuits. A report that says one error when there are nine is
the same failure as a green aggregate whose checks never executed.

### The five distinctions, kept apart

| the fault | who fixes it |
| --- | --- |
| a ref names an id that exists nowhere, and was not declared | the author, in the package |
| the record exists and is half written | whoever writes content |
| the ref is the wrong shape: a term string where an id belongs | the author |
| a value outside a list the libraries define | the author, or the library gains the value |
| declared, well formed, and the library has not caught up | nobody, in this package |

The last two rows are why the validator declines to report twice. An id
**declared in `requires`** and absent from the library reports only
`DEPENDENCY_ABSENT`; the same absence **undeclared** reports the ref error and
the mismatch. Both for one id would say the same thing under two headings and
hide which of the two it actually is.

## The prose joins the format removes

All four are live in the application, all four work today, and none of them is
expressible in a package. That is the argument for replacing them, not against.

| join | how it resolves today | in a package |
| --- | --- | --- |
| `pathway.evidence` | a display **label**, matched case-insensitively. Two records sharing a label silently become one | `evidenceRefs[].ref`, by id |
| `pathway.concept` | a `{topic, section, point}` triple matched by **prefix**. Nine of the twenty-eight authored triples resolve only that way: "rewards" finds "rewards - monetary and non-monetary, individual or group, performance pay" | `syllabusRef` and `conceptRef` |
| `learning.concepts` | bare keys hoping `subject.concepts` has them | a `learningRef` to a lesson that names concepts by id |
| `question.topic` | a display label a **keyword table** guesses a key from: four word lists, first match wins, `null` if none hit | `topicRef` |

A fifth is not a join but the same failure: a directive in neither family
resolves to `causal` by fallback, so a question commanded "Compare" is scaffolded
as a cause all the way to submission with no error anywhere. Eight commands are
in that position. An imported package may not depend on it, so
`DIRECTIVE_NO_FAMILY` is an error.

The validator rejects each old shape **by name**, not by the absence of its
replacement, because a half-migrated package would satisfy the second test.
`tests/t18.mjs` removes each planted legacy field in turn and asserts the code
stops being reported, so the check is known to be testing what it claims to.

## Vocabulary has one authority

Concept records owned fourteen distinct `{term, meaning}` pairs with real
definitions in them while the vocabulary library held nothing. Two definition
systems is one too many, so the pairs become vocabulary records and a concept
points at them by id.

They arrive carrying a course meaning and no plain meaning or example, which
makes them **usable by the Learn surface and not yet offerable in the vocabulary
panel**. That is one library with two consumers rather than two libraries, and
the manifest reports both states: 14 complete, 0 displayable. Collapsing it into
one word would either hide fourteen usable definitions or display fourteen
half-written ones.

A term string in a ref position is `VOCAB_REF_NOT_AN_ID`. `points[].terms` is
carried as `legacyTerms`, which is the name it earned: 477 strings with no
meaning anywhere, and no route to a student.

## What the transform still cannot carry

Reported by `packagize.js` rather than guessed at. These are work the contract
creates, not questions it leaves open.

    63  criterion "…" has no id: no criterion registry exists
    25  evidence references carry no authored role
    12  plan lines state no right-hand end, because they are section names
     1  objectiveWords dropped: claim right-hand ends are explicit in v1

The criterion registry is the largest single piece of work here. Stating a claim
explicitly needs stable ids for its right-hand end, and nothing has them yet.
